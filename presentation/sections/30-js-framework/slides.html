Topic 3 · The Odoo JS framework

Goals

Owl gave you components. This topic is the application they live in.

  • The web clientOne component tree, from the navbar down to your screen.
  • RegistriesHow an addon adds something the web client picks up.
  • ServicesThe code that stays alive, and how a component reaches it.
  • Client actionsA screen of your own, opened from a menu.
  • The serverThe orm plugin, controllers, and when to load.

Dashboard, the exercise that follows, uses every one of them.

The web client

Building blocks

Three layers, and the names you will keep meeting. Your addon writes the top one.

Your addon never imports the web client. It writes into a registry, and the web client reads it.

The web client

Web client

The web client is an ordinary Owl component. Everything on screen hangs below it.

web/static/src/webclient/webclient.xml

<t t-name="web.WebClient">
    <t t-if="!this.state.fullscreen">
        <NavBar/>
    </t>
    <ActionContainer/>
    <MainComponentsContainer/>
</t>

That is the whole thing. Three tags, one of them behind a t-if.

Nothing special about it: open the file and read it, then follow ActionContainer down.

Registries

Extending the web client

The primary extension mechanism: every addon registers what it adds, and the web client picks it up.

Nothing is special about web: it fills the same registries, and the standard list view is registered exactly the way yours is.

Registries

Registries

  • The primary extension point: an addon registers something, the web client picks it up.
  • One global registry, split into categories. A sequence keeps an order when order matters.

my_addon/static/src/dashboard/dashboard.js

import { registry } from "@web/core/registry";

// a category is a sub-registry
const actions = registry.category("actions");

actions.add("my_addon.dashboard", Dashboard);

// with an order, for the categories that keep one
registry.category("systray").add(
    "my_addon.counter",
    { Component: CounterItem },
    { sequence: 30 },
);
  • No importThe web client never imports your addon. It reads the registry.
  • ReplaceAdding on a key that exists, with { force: true }, overrides the standard entry.
  • LiveA registry is an EventBus: it fires on every add, so a late entry still reaches the screen.

In the console: odoo.loader.modules.get("@web/core/registry").registry.category("actions").getEntries()

Registries

Registry and Resource, in Owl 3

  • The global registry is Odoo's own, and still holds every category above. Owl 3 ships two of its own, and new code uses those.
  • Each one is a plain object, declared and exported where it belongs. No string category to spell right, and the type is checked on the way in.

Registry · keyed, like the ones above

import { Registry, t } from "@odoo/owl";

const views = new Registry({
    name: "views",
    validation: t.object({ type: t.string() }),
});

views.add("list", listView, { sequence: 10 });
views.add("list", other);                   // throws
views.add("list", other, { force: true });  // ok

views.get("list");        // throws if missing
views.get("map", null);   // or a default
views.items();          // sorted by sequence

Resource · a list, no keys

import { Plugin, Resource, t } from "@odoo/owl";

// @web/core/services, the one you meet first
export const services = new Resource({
    name: "services",
    validation: t.constructor(Plugin),
});

services.add(ReportingPlugin);  // started with the web client

// one of your own, read back with tiles.items()
const tiles = new Resource({ name: "tiles" });

tiles.add({ Component: SalesTile }, { sequence: 20 });
tiles.use({ Component: SalesTile });  // until destroy

items() is a computed, so a template that reads one follows every add and remove. use() drops the entry when the component or plugin that added it is destroyed.

Client actions

Everything on screen is an action

A menu item points at an action record. The type of that record decides who renders it.

  • TypeWhat it isRendered by
  • ir.actions.act_windowViews on a model, with a domain and a context.the view, from the views registry
  • ir.actions.clientA component of your own. Anything you like.your entry in the actions registry
  • ir.actions.reportA PDF or an HTML report.the report action
  • ir.actions.serverPython, which usually returns another action.the server, then the browser
  • ir.actions.act_urlA url to open.the browser

One service runs them all: this.action.doAction("base_setup.action_general_configuration").

Client actions

Window actions

  • Far and away the most common one: nearly every menu in Odoo opens an act_window.
  • The xml below is not read at runtime: installing the addon writes a row in ir_actions. The UI lives in the database, which most frameworks do not do.
  • It names a model and a list of view types. The web client loads those views and renders the first, with a switcher for the rest.

crm/views/crm_lead_views.xml

<record id="crm_lead_action_pipeline"
        model="ir.actions.act_window">
    <field name="name">Pipeline</field>
    <field name="res_model">crm.lead</field>
    <field name="view_mode">kanban,list,form</field>
    <field name="domain">[("type", "=", "opportunity")]</field>
    <field name="context">{"default_type": "opportunity"}</field>
</record>
  • res_modelThe model the views are built on.
  • view_modeWhich views, and in what order. The first one opens.
  • domainWhat is in scope. The user's own filters are added to it, never instead of it.
  • contextDefaults for a new record, and anything a view wants to read.

Nothing here is javascript: it is a record, and a user with the rights can edit it. Your addon writes one when a menu should open a screen it did not have to build.

Client actions

Client Actions

  • A record in Python names the action; the registry says which component renders it.
  • Layout gives your screen the control panel every other screen has.

dashboard.js, and the action record

class Dashboard extends Component {
    static template = "awesome_dashboard.Dashboard";
    // ...
}

registry.category("actions")
    .add("awesome_dashboard.dashboard", Dashboard);
<record id="dashboard" model="ir.actions.client">
    <field name="name">Dashboard</field>
    <field name="tag">awesome_dashboard.dashboard</field>
</record>

dashboard.xml

<t t-name="awesome_dashboard.Dashboard">
    <Layout display="{ controlPanel: {} }"
            className="'o_dashboard h-100'">
        <t t-set-slot="layout-buttons">
            <button class="btn btn-primary"
                    t-on-click="this.openCustomers">
                Customers
            </button>
        </t>
        the content of the dashboard
    </Layout>
</t>

A menu item points at the action record. From there on, the screen is yours.

Data

Talking to the server

The browser has no database: every piece of data is a request, and your Python method is the API.

A controller route

import { rpc } from "@web/core/network/rpc";

const stats = await rpc("/my_addon/stats", {
    period: "month",
});
@http.route("/my_addon/stats", auth="user",
            type="jsonrpc")
def stats(self, period):
    return {"orders": 42}

JSON in, JSON out.

The orm plugin

import { Component, onWillStart, signal, usePlugin } from "@odoo/owl";
import { ORM } from "@web/core/orm_plugin";

class Dashboard extends Component {
    orm = usePlugin(ORM);
    partners = signal([]);

    setup() {
        onWillStart(() => this.load());
    }

    async load() {
        const domain = [["is_company", "=", true]];
        const partners = await this.orm.searchRead(
            "res.partner", domain, ["name", "email"],
        );
        this.partners.set(partners);
    }
}

orm.call reaches any other model method.

Both go through JSON-RPC. The network tab of the browser shows every call.
