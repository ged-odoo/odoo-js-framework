Pages

What happens when a page loads

The server does most of the work. Javascript comes last.

  • 1

    A route answers

    A controller (/shop), or a website.page record (/, /contactus).

  • 2

    QWeb renders the view

    The ir.ui.view, with every inheriting view's xpaths applied, for this website and in this language.

  • 3

    The server returns HTML

    A complete page: the content is in it, for the first paint and for search engines.

  • 4

    The browser loads the bundle

    web.assets_frontend: the JS framework, and every interaction.

  • 5

    The interactions start

    One on every element that matches an interaction's selector.

The page is alive, until the next link: the server renders a whole new page, and it all starts again.

Architecture

A page, and its interactions

The page is HTML, made of snippets. Interactions attach to it, by CSS selector.

A snippet may get several interactions, or none. An interaction gets one instance per element it matches.

Interactions

What's an Interaction?

A base class to extend, on a light framework of its own: Colibri.

  • Dynamic contentFor the frontend: the website, and every other page the server renders.
  • Owl-likeThe same words, setup, willStart, t-on-click, but no Owl. The HTML is already there.
  • Lifecyclesetup, willStart, start, destroy, and helpers that clean up after themselves.
  • The builderAn interaction can run, or run differently, while the page is edited.
  • publicWidgetWhat it replaces. You still meet it in older code.

Colibri is French for hummingbird: small, light, and quick.

Architecture

Interactions, in javascript

The JS framework underneath, as in the web client. Colibri in between.

Same services as the web client: this.services.orm, this.services.notification. You write only the last box.

Interactions

Lifecycle, and the helpers

An interaction can be stopped at any time. The helpers undo what it did.

The lifecycle

  • setupSynchronous. Read the element, set your fields.
  • willStartAsynchronous. Load what the page needs, before the interaction starts.
  • startThe interaction is running: work with the page.
  • destroyIt is stopped: edit mode starts or ends, its element is removed.

Helpers that clean up after themselves

  • waitForA promise that settles only while the interaction lives.
  • addListenerA listener on any element, removed on destroy.
  • insert, renderAtElements added to the page, taken out on destroy.
  • mountComponentAn Owl component, destroyed with the interaction.
  • registerCleanupAnything else to undo.

The builder stops and restarts interactions all the time. Whatever one adds, it has to take back.

Interactions

dynamicContent's syntax

Selectors on the left, directives on the right. Familiar, if you know Owl's templates.

dynamicContent = {
    // a CSS selector, inside this.el
    ".my-selector": {
        "t-on-click": this.onClick,
        "t-att-class": () => ({ "d-none": !this.open }),
        "t-att-style": () => ({
            "background-color": this.color,
        }),
    },
    ".my-label": {
        "t-out": () => this.label,
    },
    ".my-chart": {
        "t-component": () =>
            [Chart, { someProp: "value" }],
    },
    // the interaction's own element
    _root: {
        "t-att-required": () => this.condition,
    },
};
  • SelectorEvery element that matches it, inside the interaction's own element.
  • t-on-…A listener. The handler is called on the interaction: no bind.
  • t-att-…An attribute, a class, a style, from a function.
  • t-outThe element's text.
  • t-componentAn Owl component, mounted in the element.

The functions run again on every updateContent(): after each handler, and when a waitFor settles.

Interactions

Beyond the element

A selector matches inside this.el. Named selectors reach further.

// the ones every interaction has
dynamicSelectors = {
    _root: () => this.el,
    _body: () => this.el.ownerDocument.body,
    _window: () => window,
    _document: () => this.el.ownerDocument,
};

dynamicContent = {
    _window: {
        "t-on-resize": this.onResize,
    },
    _root: {
        "t-att-required": () => this.condition
            ? true
            : Interaction.INITIAL_VALUE,
    },
};
  • _rootThe element the interaction was started on.
  • _body, _document, _windowFor what happens outside it: a scroll, a resize, a key.
  • Your ownAdd a key to dynamicSelectors, spreading the defaults, and use it in dynamicContent.
  • INITIAL_VALUEPuts back what the attribute was before the interaction started.

A listener on the window is removed with the interaction, like any other.

Owl on the website

A component in a page

For the part of a page that really is an application.

// from an interaction, where a selector matches
dynamicContent = {
    ".o_weather_chart": {
        "t-component": () =>
            [WeatherChart, { days: this.days }],
    },
};

// from an interaction, by hand
this.mountComponent(this.el, WeatherChart, { days: this.days });

// from the page: register it...
registry.category("public_components")
    .add("demo.weather_chart", WeatherChart);
<!-- ...then name it in the HTML -->
<owl-component name="demo.weather_chart"/>
  • InteractionThe HTML is the server's: there from the first paint, read by search engines, edited in the builder.
  • ComponentThe HTML is rendered in the browser: rich state, but nothing in the page until the javascript runs.
  • The ruleAn interaction by default. A component for the part that needs one.

A component on a page is the same Owl as in topic 2: signals, props, templates.
