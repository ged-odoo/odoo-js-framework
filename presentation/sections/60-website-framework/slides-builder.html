Snippets and the Builder

A snippet of your own, alive on the page, and still alive while the page is edited.

ExampleA weather forecast, from its template to its options

Snippets

Our goal

Attach behaviour to a snippet of your own, with API calls, and keep it working in edit mode.

StepsA template, the snippets dialog, an interaction, edit mode, options

Snippets

A QWeb template

A snippet is a template: the HTML dropped into the page.

views/snippets/s_weather.xml

<?xml version="1.0" encoding="UTF-8"?>
<odoo>
    <template id="demo.s_weather"
              name="Weather Forecast">
        <section class="s_weather">
            <div class="container">
                <h1 class="text-center">
                    Hello World!
                </h1>
            </div>
        </section>
    </template>
</odoo>
  • A blockA snippet the width of the page is a <section>: it gets the options every block has.
  • An inner oneA snippet dropped inside another: any element you like.
  • Bootstrapcontainer, row, text-center: its classes come with some generic options.

The class, s_weather, is what the interaction will look for.

Snippets

Into the snippets dialog

A standard xpath, on the list of snippets.

views/snippets/snippets.xml

<template id="snippets"
          inherit_id="website.snippets">
    <xpath expr="//t[@t-snippet='website.s_text_image']"
           position="before">
        <t t-snippet="demo.s_weather"
           string="Weather Forecast"
           group="content">
            <keywords>weather, forecast, climate</keywords>
        </t>
    </xpath>
</template>

__manifest__.py

"depends": ["website"],
"data": [
    "views/snippets/snippets.xml",
    "views/snippets/s_weather.xml",
],
  • t-snippetThe template to drop into the page.
  • groupThe dialog's category it is listed in.
  • keywordsAs many as you want: what the dialog's search finds it by.

Both files go in the manifest's data, or the dialog never hears of them.

Snippets

Get it in shape

A static template first: the layout, with made-up data.

<section class="pt32 pb32 s_weather"
         data-location-name="Brussels">
    <div class="container">
        <h2 class="h5">Weather in
            <span class="weather-location-name">Brussels</span>
        </h2>
        <input class="weather-location-input"
               placeholder="Another city"/>
        <div class="row align-items-center">
            <t t-foreach="[('Monday', 'clouds', '14'),
                           ('Tuesday', 'rain', '12'),
                           ('Wednesday', 'sun', '18')]"
               t-as="day">
                <div class="card col mx-2 p-0">
                    <img class="card-img-top img-fluid"
                         t-att-src="'/demo/static/img/' + day[1] + '.svg'"
                         t-att-alt="day[1]"/>
                    <div class="card-body">
                        <div class="h6" t-out="day[0]"/>
                        <p class="h5 card-title"><t t-out="day[2]"/>°C</p>
                    </div>
                </div>
            </t>
        </div>
    </div>
</section>
  • t-foreachRuns once, on the server, when the snippets are loaded. What lands in the page is plain HTML.
  • data-location-nameA setting kept in the HTML itself, for the interaction to read.
  • ClassesNo ids: a snippet can be dropped twice on the same page.
  • Bootstraprow, col, card do the layout.

The forecast is made up for now. The interaction brings the real one.

Interactions

Add an interaction

A class with a selector, registered in public.interactions.

static/src/interactions/weather.js

import { Interaction } from "@web/public/interaction";
import { registry } from "@web/core/registry";
import { rpc } from "@web/core/network/rpc";

export class Weather extends Interaction {
    static selector = ".s_weather";
    dynamicContent = {
        ".weather-location-name": {
            "t-out": () => this.locationName,
        },
    };

    setup() {
        this.locationName = this.el.dataset.locationName;
    }

    async willStart() {
        this.days = await rpc("/demo/get_weather", {
            location: this.locationName,
        });
    }
    ...
}

registry
    .category("public.interactions")
    .add("demo.weather", Weather);
  • selectorA CSS selector: one instance per element it matches.
  • selectorHasOnly the matches that contain an element matching this one.
  • selectorNotHasOnly the ones that do not.
  • this.elThe matched element: here the section, and its data-location-name.
  • willStartThe interaction waits for the forecast before it starts.

/demo/get_weather is a JSON route of the addon's own controller.

Interactions

Add some listeners

A t-on-… in dynamicContent, and waitFor around anything asynchronous.

class Weather extends Interaction {
    ...
    dynamicContent = {
        ".weather-location-input": {
            "t-on-change": this.onInputChange,
        },
    };

    async onInputChange(ev) {
        this.locationName = ev.currentTarget.value;
        this.days = await this.waitFor(
            rpc("/demo/get_weather", {
                location: this.locationName,
            }),
        );
        this.updateWeather();
    }
}

Modifiers, after the event's name

  • .preventpreventDefault()
  • .stopstopPropagation()
  • .capture, .once, .passiveAs for addEventListener.
  • .noUpdateNo updateContent() after the handler: you call it yourself.
  • Combinedt-on-click.prevent.stop

No bind. And if the interaction is destroyed while the request runs, waitFor never settles: no code runs on a dead snippet.

Edit mode

Also in edit mode

While a page is edited, its interactions are stopped. Unless you say otherwise.

static/src/interactions/weather.js

// start the interaction in edit mode too
registry
    .category("public.interactions.edit")
    .add("demo.weather", {
        Interaction: Weather,
    });

__manifest__.py

"assets": {
    "web.assets_frontend": [
        "demo/static/src/interactions/**/*",
    ],
},
  • The edit registryThe interactions listed there run while the page is edited, under the same key.
  • The bundleThe frontend one: every page loads it, the one in the builder too.

The simplest case: the same behaviour, edited or not.

Edit mode

An edit interaction

A mixin takes the interaction, and returns what it should be in edit mode.

static/src/interactions/weather.edit.js

import { registry } from "@web/core/registry";
import { Weather } from "./weather";

const WeatherEdit = (I) =>
    class extends I {
        dynamicContent = {
            ...this.dynamicContent,
            // no listener while the page is edited
            ".weather-location-input": {},
        };
    };

registry
    .category("public.interactions.edit")
    .add("demo.weather", {
        Interaction: Weather,
        mixin: WeatherEdit,
    });

__manifest__.py

"assets": {
    "web.assets_frontend": [
        "demo/static/src/interactions/**/*",
        ("remove", "demo/static/src/**/*.edit.js"),
    ],
    "website.assets_inside_builder_iframe": [
        "demo/static/src/**/*.edit.js",
    ],
},
  • The mixinA function, class in, class out: it extends whatever the interaction is.
  • .edit.jsLoaded only inside the builder's iframe, and kept out of the public bundle.

One entry per key in the edit registry: this one replaces the previous slide's.

Architecture

The website builder

The page runs in an iframe, with its edit interactions. The options sit beside it.

Two sides, two worlds: the page is HTML with interactions, the builder around it is Owl.

Architecture

The builder, in javascript

An editor made of plugins, and the options beside it. A plugin brings actions, an option runs them.

Built-in actions cover most options: a class, a style, an attribute, a data attribute. A plugin is for the rest.

The builder

Options of your own

Go further: let whoever edits the page choose the city.

  • An optionA component and its template: a row per setting, a text input, a select, a pair of buttons.
  • Its placeOn .s_weather, set in the website.BuilderOptions template.
  • An actionWhat a value does to the snippet: a class, a style, a data attribute, or one of your own, brought by a plugin.
  • Back in the pageDefault location writes data-location-name. The interaction reads it in setup.

The options write the HTML, the interaction reads it. Neither knows the other.

The builder

An option, in code

A component in website-options, and a line that puts it on the snippet.

static/src/builder/weather_option.js

import { BaseOptionComponent } from "@html_builder/core/base_option_component";
import { registry } from "@web/core/registry";

export class WeatherOption extends BaseOptionComponent {
    static id = "weather_option";
    static template = "demo.WeatherOption";
}

registry
    .category("website-options")
    .add(WeatherOption.id, WeatherOption);

__manifest__.py

"assets": {
    "website.website_builder_assets": [
        "demo/static/src/builder/**/*",
    ],
},

static/src/builder/weather_option.xml

<t t-name="demo.WeatherOption">
    <BuilderRow label.translate="Default location">
        <BuilderTextInput
            dataAttributeAction="'locationName'"/>
    </BuilderRow>
</t>

<t t-inherit="website.BuilderOptions"
   t-inherit-mode="extension">
    <xpath expr="//t[@id='snippet_specific_options']"
           position="after">
        <weather_option selector=".s_weather"/>
    </xpath>
</t>

dataAttributeAction is built in: no plugin needed here. It writes data-location-name, the attribute the interaction reads.
