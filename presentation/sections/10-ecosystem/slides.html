Decision guide

When javascript is the right answer

The rule has exceptions.

  • Customizing a field

    The standard widgets cannot show what you need.

  • A screen

    It is not a view: a dashboard, a game, a custom workspace.

  • Website behaviour

    A public page needs interaction in the browser.

  • The point of sale

    The cash-register experience itself must change.

DefaultEverything else is a Python job.

JS in Odoo

Javascript on the website

// my_addon/static/src/interactions/read_more.js
import { Interaction } from "@web/public/interaction";
import { registry } from "@web/core/registry";

export class ReadMore extends Interaction {
    static selector = ".o_read_more";
    dynamicContent = {
        "button": { "t-on-click": this.toggle },
        ".o_more": { "t-att-class": () => ({ "d-none": !this.open }) },
    };

    setup() {
        this.open = false;
    }

    toggle() {
        this.open = !this.open;
    }
}

registry.category("public.interactions").add("my_addon.read_more", ReadMore);
  • InteractionBehaviour on HTML the server already rendered. Website only.
  • SelectorOne instance on every element that matches it, started with the page.
  • OwlFor complex parts: a component, mounted by <owl-component name="…"/> in the page.

Interactions for the small things, Owl components for the complex ones.

Assets

Assets and bundles

# __manifest__.py
{
    "name": "My addon",
    "depends": ["web"],
    "assets": {
        "web.assets_backend": [
            "my_addon/static/src/**/*",
        ],
    },
}
  • ManifestRegisters each file into a named bundle.
  • Main bundlesOne per codebase: web.assets_backend, web.assets_frontend, point_of_sale._assets_pos.
  • No bundleA file in no bundle is never loaded.

Glob patterns are fine: my_addon/static/src/**/* takes the whole folder.

Assets

No build step

The Odoo server is the bundler. No npm, no webpack, no Node.js to install. The XML rides inside the js bundle, registered as a module of its own.

Templates

QWeb, two engines

QWeb is an XML templating language: directives are attributes on ordinary tags. One syntax, two engines that read it.

  • QWeb in Python

    Reports, website pages, emails. Rendered on the server, page by page.

    t-field · t-call

  • QWeb in Owl

    Components. Compiled in the browser the first time a template is needed, then re-rendered whenever the state it reads changes.

    t-on-click · t-ref · t-call-slot

An XML file goes in the bundle like any other file.

Modules

Importing from another addon

Every file is an ES module: import and export, no globals.

// my_addon/static/src/dashboard/dashboard.js
import { Component } from "@odoo/owl";
import { registry } from "@web/core/registry";
import { Counter } from "../counter/counter";

export class Dashboard extends Component {
    static template = "my_addon.Dashboard";
    static components = { Counter };
}

registry
    .category("actions")
    .add("my_addon.dashboard", Dashboard);
  • Another addon@web/core/registry is web/static/src/core/registry.js. The addon must be in your depends.
  • Your own addonA path relative to the file: ../counter/counter. @my_addon/counter/counter works too.
  • A library@odoo/owl, provided by web.

Modules are resolved by odoo.loader, in the browser, at startup.

The framework

New in Odoo 20: Owl 3

Odoo is moving from Owl 2 to Owl 3. It landed in saas-19.4, Odoo 20 runs on it, and it is a separate library rather than a superset: Owl 3 does not run Owl 2 code.

Highlights

signal, plugins, typed props and more.

Migration

Owl 2 to Owl 3

  • Not compatibleOwl 3 does not run Owl 2 code. The two are separate libraries.
  • Mostly migratedMost of Odoo is on Owl 3. A compatibility layer runs the rest, mostly.
  • TemporaryThe layer goes as soon as possible.

Odoo 19.0 stays on Owl 2. saas-19.4 and later run Owl 3.
