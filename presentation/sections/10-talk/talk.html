Rule one

The first rule of customizing Odoo in javascript is…

Rule one · Before reaching for javascript

Do it in Python.

The server is usually the simpler, safer extension point.

Decision guide

When javascript is the right answer

The rule has exceptions.

  • Customizing a field

    The standard widgets cannot show what you need.

  • A screen

    It is not a view: a dashboard, a game, a custom workspace.

  • Website behaviour

    A public page needs interaction in the browser.

  • The point of sale

    The cash-register experience itself must change.

DefaultEverything else is a Python job.

The landscape

Javascript in Odoo

Assets

Assets and bundles

# __manifest__.py
{
    "name": "My addon",
    "depends": ["web"],
    "assets": {
        "web.assets_backend": [
            "my_addon/static/src/**/*",
        ],
    },
}
  • ManifestRegisters each file into a named bundle.
  • Main bundlesOne per codebase: web.assets_backend, web.assets_frontend, point_of_sale._assets_pos.
  • No bundleA file in no bundle is never loaded.

Glob patterns are fine: my_addon/static/src/**/* takes the whole folder.

Assets

No build step

The Odoo server is the bundler. No npm, no webpack, no Node.js to install. The XML rides inside the js bundle, registered as a module of its own.

Templates

QWeb, two engines

QWeb is an XML templating language: directives are attributes on ordinary tags. One syntax, two engines that read it.

  • QWeb in Python

    Reports, website pages, emails. Rendered on the server, page by page.

    t-field · t-call

  • QWeb in Owl

    Components. Compiled in the browser the first time a template is needed, then re-rendered whenever the state it reads changes.

    t-on-click · t-ref · t-call-slot

An XML file goes in the bundle like any other file.

What is Owl?

A JavaScript framework, in the family of React and Vue.

It defines

  • ComponentsA base Component class.
  • ReactivityBuilt on signals.
  • TemplatesAn extension of QWeb.
  • HooksAnd utility functions.

Open source, at github.com/odoo/owl. The Odoo web client is built on it.

Components

A Counter component

A component is a class and a template.

counter.js

import { Component, signal } from "@odoo/owl";

class Counter extends Component {
    static template = "my_module.Counter";

    counter = signal(0);

    increment() {
        this.counter.set(this.counter() + 1);
    }
}

counter.xml

<templates xml:space="preserve">
    <t t-name="my_module.Counter">
        <p>
          Counter: <t t-out="this.counter()"/>
        </p>
        <button
            class="btn btn-primary"
            t-on-click="this.increment">
          Increment
        </button>
    </t>
</templates>

The template name in static template is what ties the two files together.

Template syntax

Components

Props, and their validation

  • The parent passes data down. The child never writes to it.
  • useProps declares the shape. A missing or wrong prop fails loudly, in dev mode.

The child declares what it accepts

import { useProps, t } from "@odoo/owl";

export class ProductCard extends Component {
    static template = "tutorial.ProductCard";

    props = useProps({
        name: t.string(),
        price: t.number(),
        image: t.string().optional("📦"),
    });
}

The parent passes them, as JavaScript

<t t-name="tutorial.Root">
    <ProductCard
        name="this.keyboard.name"
        price="this.keyboard.price"
        image="this.keyboard.image"/>
</t>

<!-- in the child -->
<div t-out="this.props.name"/>

To send something up, the parent passes a function: callback props, in Building an Application.

Reactivity

Derived values: computed

  • A value built from other signals, read like a signal: this.isValid().
  • Recomputed on its own, only when what it read has changed.
  • t-model binds an input to a signal, both ways.

some_component.js

import { signal, computed } from "@odoo/owl";

class SomeComponent extends Component {
    name = signal("");
    email = signal("");

    isValid = computed(() => {
        return this.name()
            && this.email().includes("@");
    });
}

some_component.xml

<t t-name="my_module.SomeComponent">
    <input t-model="this.name"
           placeholder="Name"/>
    <input t-model="this.email"
           placeholder="Email"/>
    <div t-out="this.isValid()
                ? 'Valid' : 'Invalid'"/>
</t>

Read a computed like a signal. Never set it: it follows its inputs.

Lists

A list of components

  • t-foreach over the data, one child component per item.
  • t-key is how Owl tells the items apart between two renders. Never skip it.

todo_list.js

export class TodoList extends Component {
    static template = "tutorial.TodoList";
    static components = { TodoItem };

    todos = signal.Array([
        { id: 1, text: "Buy milk" },
        { id: 2, text: "Walk the dog" },
    ]);
}

todo_list.xml

<ul class="todo-list">
    <t t-foreach="this.todos()"
       t-as="todo"
       t-key="todo.id">
        <TodoItem todo="todo"/>
    </t>
</ul>

Owl keeps the child whose key is still there, and creates or drops the rest.

Lists

When push renders nothing

A plain array is not reactive. Owl has no way to know it changed.

  • signal.Array and signal.Object track their own content: push, splice, a key set or deleted.

A plain array

// nothing happens on screen
todos = [
    { id: 1, text: "Buy milk" },
];

addTodo(text) {
    this.todos.push({ id: 2, text });
}

A collection signal

// the list re-renders
todos = signal.Array([
    { id: 1, text: "Buy milk" },
]);

addTodo(text) {
    this.todos().push({ id: 2, text });
}

The wrapping is shallow: what is inside stays a plain object, and stays untracked.

Lists

Reactive data inside the list

Ticking the checkbox changes nothing: completed is a plain boolean, one level below what signal.Array tracks.

  • A signal is a value. It can sit in an object, be passed as a prop, be bound with t-model.

The data, and the props of the item

todos = signal.Array([
    { id: 1, text: "Buy milk",
      completed: signal(false) },
]);

// in TodoItem
props = useProps({
    todo: t.object({
        id: t.number(),
        text: t.string(),
        completed: t.signal(),
    }),
});

todo_item.xml

<li class="todo-item"
    t-att-class="{
      completed: this.props.todo.completed()
    }">
    <input type="checkbox"
           t-model="this.props.todo.completed"/>
    <span t-out="this.props.todo.text"/>
</li>

Make reactive what actually changes, and nothing else: text and id stay plain.

Refs

Reaching the DOM

  • signal.ref() plus t-ref: the element lands in the signal once mounted.
  • Before mounting it is null, which is why the DOM is touched in onMounted.

todo_list.js

import { signal, onMounted } from "@odoo/owl";

export class TodoList extends Component {
    input = signal.ref();

    setup() {
        onMounted(() => {
            this.input().focus();
        });
    }
}

todo_list.xml

<input class="todo-input"
       t-ref="this.input"
       placeholder="What needs to be done?"/>

A ref is a signal: read it with this.input(), like any other.

Refs

Writing your own hook

  • A plain function that calls other hooks, named use… by convention.
  • It is how behaviour is shared between components, without a base class.

utils.js

import { onMounted } from "@odoo/owl";

export function useAutofocus(ref) {
    onMounted(() => {
        ref()?.focus();
    });
}

todo_list.js

import { useAutofocus } from "./utils";

export class TodoList extends Component {
    input = signal.ref();

    setup() {
        useAutofocus(this.input);
    }
}

Called while the component is being created: in setup, or as a class field. Not later, from a handler or a method.

Callback props

Talking to the parent

The child displays a todo, but the parent owns the list. So the parent deletes, and the child asks.

A function is a prop like any other: onDelete: t.function().optional().

Picking one

Reacting to a change

Both track the signals they read, and run again when those change. The difference is what you want out of them.

computed

  • You want a value.
  • Read it like a signal: this.remaining().
  • No side effect, ever.
remaining = computed(() =>
    this.todos().filter((t) => !t.completed()).length
);

useEffect

  • You want a side effect.
  • Saving, logging, a third-party library.
  • Returns nothing useful.
useEffect(() => {
    localStorage.setItem("todos", serialize(this.todos()));
});

Plugins

Sharing state and logic between components

A component renders. Everything else, the data and the rules, belongs somewhere a second component can reach.

A plugin is a class with signals and methods. Every component that asks gets the same instance.

Plugins

A plugin, in code

  • providePlugins at the top, once: it opens the plugins to that component and its children.
  • usePlugin anywhere below, in a component or in a plugin.

todo_list_plugin.js

import { Plugin, signal, usePlugin } from "@odoo/owl";
import { StoragePlugin } from "../storage_plugin";

export class TodoListPlugin extends Plugin {
    todos = signal.Array([]);

    storage = usePlugin(StoragePlugin);

    addTodo(text) {
        text = text.trim();
        if (text) {
            this.todos().push({ ... });
        }
    }
}

todo_list.js, todo_item.js

export class TodoList extends Component {
    setup() {
        providePlugins([TodoListPlugin]);
        this.todoList = usePlugin(TodoListPlugin);
    }
}

// and in the child, no prop needed
export class TodoItem extends Component {
    todoList = usePlugin(TodoListPlugin);
}

No prop drilling: the child reaches the plugin on its own.

Picking one

Four ways to be reactive

One dependency tracker underneath, four shapes on top. Pick by the shape of your data.

  • signal(0)

    A single value.

    Tracks the value.

  • signal.Array([])

    A list you add to.

    Tracks its own items, shallow.

  • signal.Object({})

    A flat bag of keys.

    Tracks its own keys, shallow.

  • proxy({...})

    A nested tree of settings.

    Tracks every level, recursively.

With a proxy, a plain write notifies: viewPrefs.sort.direction = "desc". In a template, t-model.proxy="this.viewPrefs.sort.by".

Generic components

A component whose content is somebody else's: slots.

Slots

Content the caller writes

  • A Card draws the frame. What goes inside is different at every call site.
  • Props pass data down: a string, a number, a record. They cannot pass a paragraph and a button with a handler on it.

root.xml — what we want to be able to write

<t t-name="tutorial.Root">
    <Card>
        <p>Some quick example text.</p>
        <a class="btn btn-primary"
           t-on-click="this.goSomewhere">
          Go somewhere
        </a>
    </Card>
</t>
  • MarkupA paragraph, a button, another component — whatever this screen needs.
  • Its ownthis.goSomewhere is the Root's method. The Card never hears about it.
  • Every callThe next <Card/> holds something else entirely.

Owl calls that a slot: the generic component leaves a hole, and whoever uses it fills the hole.

Slots

A slot is a hole in a template

  • The generic component says where the content goes, with t-call-slot. The caller says what it is.

card.xml — the generic component

<t t-name="tutorial.Card">
    <div class="card">
        <div class="card-body">
            <t t-call-slot="default"/>
        </div>
    </div>
</t>
  • defaultEverything the caller wrote between <Card> and </Card>.
  • Nothing elseThe Card is seven lines of markup, and no javascript at all.
  • ReusableEvery screen that needs a card frame now has one.

The content is rendered where it was written: this.goSomewhere is the Root's method, not the Card's.

Slots

Named slots, and optional ones

  • t-set-slot names a piece of content. Everything left over is the default slot.
  • What the caller gave you is readable: this.props.slots, keyed by slot name.

card.xml

<t t-name="tutorial.Card">
  <div class="card">
    <div class="card-body">
      <h5 class="card-title"
          t-if="this.props.slots.title">
        <t t-call-slot="title"/>
      </h5>
      <t t-call-slot="default"/>
    </div>
  </div>
</t>

root.xml

<Card>
    <t t-set-slot="title">Card title</t>
    <p>Some quick example text.</p>
</Card>

<!-- no title given: the h5 is not
     rendered at all -->
<Card>
    <p>Just a body.</p>
</Card>

A slot can carry a default too: <t t-call-slot="title">Untitled</t> renders that when the caller gave nothing.

Registries

Extending the web client

The primary extension mechanism: every addon registers what it adds, and the web client picks it up.

Nothing is special about web: it fills the same registries, and the standard list view is registered exactly the way yours is.

Registries

Registries

  • The primary extension point: an addon registers something, the web client picks it up.
  • One global registry, split into categories. A sequence keeps an order when order matters.

my_addon/static/src/dashboard/dashboard.js

import { registry } from "@web/core/registry";

// a category is a sub-registry
const actions = registry.category("actions");

actions.add("my_addon.dashboard", Dashboard);

// with an order, for the categories that keep one
registry.category("systray").add(
    "my_addon.counter",
    { Component: CounterItem },
    { sequence: 30 },
);
  • No importThe web client never imports your addon. It reads the registry.
  • ReplaceAdding on a key that exists, with { force: true }, overrides the standard entry.
  • LiveA registry is an EventBus: it fires on every add, so a late entry still reaches the screen.

In the console: odoo.loader.modules.get("@web/core/registry").registry.category("actions").getEntries()

Registries

Registries

Registry and Resource, in Owl 3

  • The global registry is Odoo's own, and still holds every category above. Owl 3 ships two of its own, and new code uses those.
  • Each one is a plain object, declared and exported where it belongs. No string category to spell right, and the type is checked on the way in.

Registry · keyed, like the ones above

import { Registry, t } from "@odoo/owl";

const views = new Registry({
    name: "views",
    validation: t.object({ type: t.string() }),
});

views.add("list", listView, { sequence: 10 });
views.add("list", other);                   // throws
views.add("list", other, { force: true });  // ok

views.get("list");        // throws if missing
views.get("map", null);   // or a default
views.items();          // sorted by sequence

Resource · a list, no keys

import { Plugin, Resource, t } from "@odoo/owl";

// @web/core/services, the one you meet first
export const services = new Resource({
    name: "services",
    validation: t.constructor(Plugin),
});

services.add(ReportingPlugin);  // started with the web client

// one of your own, read back with tiles.items()
const tiles = new Resource({ name: "tiles" });

tiles.add({ Component: SalesTile }, { sequence: 20 });
tiles.use({ Component: SalesTile });  // until destroy

items() is a computed, so a template that reads one follows every add and remove. use() drops the entry when the component or plugin that added it is destroyed.

Client actions

Everything on screen is an action

A menu item points at an action record. The type of that record decides who renders it.

  • TypeWhat it isRendered by
  • ir.actions.act_windowViews on a model, with a domain and a context.the view, from the views registry
  • ir.actions.clientA component of your own. Anything you like.your entry in the actions registry
  • ir.actions.reportA PDF or an HTML report.the report action
  • ir.actions.serverPython, which usually returns another action.the server, then the browser
  • ir.actions.act_urlA url to open.the browser

One service runs them all: this.action.doAction("base_setup.action_general_configuration").

Client actions

Window actions

  • Far and away the most common one: nearly every menu in Odoo opens an act_window.
  • The xml below is not read at runtime: installing the addon writes a row in ir_actions. The UI lives in the database, which most frameworks do not do.
  • It names a model and a list of view types. The web client loads those views and renders the first, with a switcher for the rest.

crm/views/crm_lead_views.xml

<record id="crm_lead_action_pipeline"
        model="ir.actions.act_window">
    <field name="name">Pipeline</field>
    <field name="res_model">crm.lead</field>
    <field name="view_mode">kanban,list,form</field>
    <field name="domain">[("type", "=", "opportunity")]</field>
    <field name="context">{"default_type": "opportunity"}</field>
</record>
  • res_modelThe model the views are built on.
  • view_modeWhich views, and in what order. The first one opens.
  • domainWhat is in scope. The user's own filters are added to it, never instead of it.
  • contextDefaults for a new record, and anything a view wants to read.

Nothing here is javascript: it is a record, and a user with the rights can edit it. Your addon writes one when a menu should open a screen it did not have to build.

Client actions

Plugins

The code that outlives a screen, and what has to be loaded before the first render.

Services

Plugins and services

A component is created and destroyed with its screen. A service is started once, with the web client, and outlives every screen.

  • State that must survive a screen change, or be shared between two of them, belongs in a service.

The older shape, still everywhere

import { registry } from "@web/core/registry";

const myService = {
    dependencies: ["notification"],
    start(env, { notification }) {
        return { doSomething() { /* ... */ } };
    },
};
registry.category("services").add("my", myService);

// in a component
this.my = useService("my");

Owl 3: a global plugin

import { Plugin, usePlugin } from "@odoo/owl";
import { NotificationPlugin }
    from "@web/core/notifications/notification_plugin";
import { services } from "@web/core/services";

export class MyPlugin extends Plugin {
    notification = usePlugin(NotificationPlugin);

    doSomething() { /* ... */ }
}

services.add(MyPlugin);

// in a component
my = usePlugin(MyPlugin);

Write plugins. Read both: plenty of services are still in their old shape, and every ported one keeps a useService alias for the code that has not moved yet.

Services

The ones already there

  • PluginWhat it gives youImported from

  • NotificationPluginThe toasts in the top right corner.@web/core/notifications/notification_plugin
  • DialogPluginA dialog over the current screen.@web/core/dialog/dialog_plugin
  • EffectPluginThe rainbowman, and the other effects.@web/core/effects/effect_plugin

Services

Defining a plugin

  • A class extending Plugin, and one line to start it with the web client. Nothing else refers to it.

my_addon/static/src/reporting_plugin.js

import { Plugin, onWillStart, signal, usePlugin } from "@odoo/owl";
import { ORM } from "@web/core/orm_plugin";
import { services } from "@web/core/services";

export class ReportingPlugin extends Plugin {
    orm = usePlugin(ORM);
    stats = signal.Object({});

    setup() {
        onWillStart(() => this.reload());
    }

    async reload() {
        const stats = await this.orm.call("my.model", "get_stats");
        this.stats.set(stats);
    }
}

services.add(ReportingPlugin);
  • StateSignals, as in a component. Everything that reads one follows it.
  • DependenciesusePlugin in a field, the same call a component makes. What it names is started if it has not been.
  • setupListeners and subscriptions. onWillStart works here too: the web client waits for it.
  • CleanupSignals, computeds and useListener undo themselves. For the rest, onWillDestroy.
  • services.addStarted once with the web client, and alive until the tab is closed.

No manifest entry, no registration order: the file is in the bundle, the class is in services, it runs.

Services

A plugin that only does something

It holds no state and nobody reads it. It exists because the web client started it.

my_addon/static/src/tick_tock_plugin.js

import { Plugin, onWillDestroy, usePlugin } from "@odoo/owl";
import { NotificationPlugin }
    from "@web/core/notifications/notification_plugin";
import { services } from "@web/core/services";

class TickTockPlugin extends Plugin {
    notification = usePlugin(NotificationPlugin);

    setup() {
        let counter = 1;
        const id = setInterval(() => {
            this.notification.add(`Tick Tock ${counter++}`);
        }, 5000);
        onWillDestroy(() => clearInterval(id));
    }
}

services.add(TickTockPlugin);
  • AloneNo component, no template, no screen. Install the addon, reload, and the toasts start.
  • Reaching outusePlugin(NotificationPlugin) from inside a plugin: plugins compose the same way components use them.
  • Giving backThe interval would outlive the plugin. onWillDestroy runs on the way out, in reverse order.

In the old shape, that dependency was a dependencies: ["notification"] key.

Useful in practice for anything that listens: the bus, a watchdog on the assets, a keyboard shortcut of your own.

Services

Reaching one from a component

  • usePlugin(Class) hands back the instance, with everything on it: the class you imported is the documentation.

uploader.js

import { Component, usePlugin } from "@odoo/owl";
import { ORM } from "@web/core/orm_plugin";
import { NotificationPlugin }
    from "@web/core/notifications/notification_plugin";

export class Uploader extends Component {
    static template = "my_addon.Uploader";

    orm = usePlugin(ORM);
    notification = usePlugin(NotificationPlugin);

    async onUpload(data) {
        const [id] = await this.orm.create(
            "ir.attachment", [data],
        );
        this.notification.add(`Uploaded ${id}`);
    }
}
  • WhereA class field, or setup(). Never anywhere else: it has to run while the component is being created.
  • No stringAn import, so the editor follows it to the class and every method it has.
  • ReactiveRead this.stats.stats() from a plugin in your template and the component re-renders when it changes. Owl 2 needed useState(useService(…)); this does not.
  • ScopedAn orm call whose component is destroyed before it answers is dropped, not applied to a screen that is gone.

One instance per tab: two components calling usePlugin(ReportingPlugin) get the same object, cache included.

Loading before the first render

  • onWillStart runs once, before the component is rendered. The screen waits for the promise.
  • Owl renders the whole tree in one pass: every branch waits, then the DOM is touched once.

dashboard.js

import { Component, onWillStart, usePlugin } from "@odoo/owl";
import { ReportingPlugin } from "./reporting_plugin";

export class Dashboard extends Component {
    static template = "my_addon.Dashboard";

    reporting = usePlugin(ReportingPlugin);

    setup() {
        onWillStart(() => this.reporting.load());
    }
}

dashboard.xml

<t t-name="my_addon.Dashboard">
    <p t-out="this.reporting.someData()"/>
</t>
  • OncePer mounting. Come back to the screen and it runs again, which is why the data, and its cache, live in the plugin.
  • LaterA slow call that must not block: render, then let the plugin set its signal when it lands.
  • NeverNo request in setup without awaiting it somewhere: the render will not wait for it.

One rule: the data a screen cannot render without is loaded in onWillStart.

What a view is made of, and how to customize views and fields.

Topic 3 · Part 1

Views and Fields

What a view is made of whatever its type, the model behind the relational ones, and the components that plug into them.

Views

What a view does

  • Loads data

    Through the ORM, from the model it is set on.

  • Structures it

    According to an arch: an xml document, stored in ir.ui.view.

  • Shows it

    Usually records and fields, though not always.

  • Edits

    Sometimes: a view can be read-only by design.

The debug tools (developer mode) are the fast way to read a view's actual arch.

Views

View architecture

The same shape whatever the type: a controller on top, a renderer and a model under it.

The renderer never calls the server, and the model never draws anything. They meet in the controller.

Views

The pieces of a view

  • ControllerThe main component: owns the model, holds the control panel and the renderer.
  • RendererBelow the control panel, the component that actually represents the data.
  • ModelLoads data from the database, and writes changes back to it.
  • ArchParserReads the arch and extracts the information the rest needs.
  • CompilerFor some views: turns the arch into an actual Owl template.

A view type registers all five together, under one name.

Views

Registering a view type

The same shape for every view: kanban, list, form...

export const kanbanView = {
    type: "kanban",
    ArchParser: KanbanArchParser,
    Controller: KanbanController,
    Model: RelationalModel,
    Renderer: KanbanRenderer,
    Compiler: KanbanCompiler,
    buttonTemplate: "web.KanbanView.Buttons",
    props: (genericProps, view) => {
        // whatever this returns is what the
        // controller is then created with
    },
};

registry.category("views").add("kanban", kanbanView);

The view's own props function is what feeds the controller the arch, the fields, the domain...

Views

Example: the form view

The same names, in the tree an actual form view mounts.

One component per <field> in the arch, and an x2many holds a renderer of its own: the same architecture, one level down.

Views

Standard flows

Editing a value

  • The user changes a value in a field's input.
  • That field instance calls update on props.record.
  • The relational model is notified of the change.
  • If there are onchanges, the server is called to get the new values.
  • The model updates, and every changed field rerenders.

Changing a domain in a list

  • The user changes the search filters.
  • WithSearch updates its domain.
  • The controller is updated with the new domain as a prop.
  • The relational model refetches the data.
  • The renderer updates, destroying its previous components.

Both flows go through the model - it is the one source of truth for a view's data.

Views

Odoo views

Three of them show records and their fields. The rest aggregate, schedule or plot the same data.

Relational views

  • form

    One record, and its fields.

  • list

    Many records, in rows.

  • kanban

    Many records, as cards.

The others

  • graph

    Totals, as a chart.

  • pivot

    Totals, in a table.

  • calendar

    Records on dates.

  • activity

    What is due, per record.

  • gantt

    Spans on a timeline.

  • map

    Records on a map.

Only the three on the left share the RelationalModel; the others bring their own. gantt and map are enterprise.

The model

The RelationalModel

One model behind form, list and kanban. What it manages is not a screen: it is collections of records, and the relations between them.

Records, groups of records and x2many lists are all DataPoints — one tree, loaded and saved in one call. many2many behaves like one2many here.

Fields

A field is a component

One <field> in the arch, one component on screen: a child of the renderer, bound to one value of one record.

the arch, in ir.ui.view

<form>
    <group>
        <field name="name"/>
        <field name="email"/>
        <field name="category_id"
               widget="many2many_tags"/>
    </group>
</form>

what the renderer mounts

<!-- FormRenderer, compiled from the arch -->
<Field name="'name'"
       record="this.props.record"/>
<Field name="'email'"
       record="this.props.record"/>
<Field name="'category_id'"
       record="this.props.record"/>

Simplified: the compiler also hands each one its id, the arch info that describes it, and the view's readonly state.

Same Field component every time. Which component it then renders is what the widget attribute, or the field's type, decides.

Customizing views and fields

Changing what a standard field or view does, without forking it.

Customizing views

Two strategies: monkey-patching, or subclassing.

Customizing views

Which one, and when

  • Monkey-patching

    Modify in place. Every instance of that view or field changes, everywhere in the web client, for every user.

  • Subclassing

    Create a variation, and use it on the screens that asked for it: a js_class on the view, a widget on the field.

Subclass when you can: what you add is opt-in, and the standard behaviour is still there for everyone who did not ask.

Fields

Subclassing a field

Extend the component, extend its props, change what needs changing.

hidden_hash_field.js

class HiddenHashField extends HashField {
    props = useProps({
        ...hashFieldProps,
        isHidden: t.boolean().optional(),
    });
}

const hiddenHashField = {
    ...hashField,
    component: HiddenHashField,
    extractProps(fieldInfo) {
        const props = hashField.extractProps(fieldInfo);
        props.isHidden = fieldInfo.options.should_hide;
        return props;
    },
};

registry.category("fields").add("hidden-hash", hiddenHashField);

The DOM

Where an event is caught

A click on a button is also a click on everything around it. The phase decides who hears it first.

setup() {

  • BubblingBack up. t-on-click listens here, and a handler can stop the trip.
  • CleanupuseListener removes it when the component goes. addEventListener does not.

The toolbox

Talking to the user

Four standard ways. None of them is a component you have to write.

Assets

Everything under static/ is served

Two ways into the browser: the page fetches the file by url, or a bundle carries it.

  • static/srcYour javascript, scss and xml templates. Bundled, never fetched one by one.
  • static/libA third-party library, as it was downloaded. Bundled too, or loaded on demand with loadJS.
  • static/imgImages and fonts. Fetched by url, when something on the page asks for one.
  • static/testsTest files, in a bundle the web client never loads.

No controller and no access rule in front of it: /my_addon/static/img/logo.png is a public url. Nothing private goes under static/.

Assets

Bundles

  • A bundle is an ordered list of files — js, scss, css, xml — declared in __manifest__.py.
  • Your code runs because it is in one. Nothing else loads it.

my_addon/__manifest__.py

{
    'assets': {
        'web.assets_backend': [
            'my_addon/static/src/**/*',
            ('remove', 'my_addon/static/src/heavy/**/*'),
        ],
        # a bundle of your own, loaded when it is needed
        'my_addon.heavy': [
            'my_addon/static/src/heavy/**/*',
        ],
    },
}
  • web.assets_backendThe web client. Nearly everything written in this masterclass.
  • web.assets_frontendThe public website: another application, another bundle.
  • web.assets_unit_testsTest files, run by hoot, out of the way of the client.
  • your ownAny name you like. LazyComponent loads it the first time a screen needs it.

Ordered, and editable: ('before', …), ('after', …), ('replace', …) and ('remove', …) place a file, or take one out of a bundle you do not own.

Topic 4 · Customizing the UI

Customizing the UI

Changing what the web client already does, and taking the places it leaves open.

Extension points

Extending instead of rewriting

There is no _inherit in javascript. Four tools instead, of two kinds.

Add something of your own

  • Registries

    Add or replace a field widget, a view, a service, a systray item.

  • extends

    Subclass a component, then register the subclass.

The standard code is untouched, and what you added is used where it was asked for.

Change what is already there

  • patch()

    Change a method on an existing class or object.

  • t-inherit-mode="extension"

    Change an existing template in place, with an xpath.

In place, everywhere, for everyone — including the screens you have never seen.

The left column first. Reach right only when the standard code left you no hook.

Patching

When there is no hook

  • patch(target, extension) replaces properties and keeps the originals reachable through super.
  • It is global: every use of that class changes, in every addon, for every user.

my_addon/static/src/patches.js

import { patch } from "@web/core/utils/patch";
import { FormController } from "@web/views/form/form_controller";

patch(FormController.prototype, {
    setup() {
        super.setup(...arguments);
        // ... whatever you need
    },

    get canEdit() {
        return super.canEdit && this.props.resId;
    },
});
  • Prototypepatch(MyClass.prototype, …) for methods and getters, patch(MyClass, …) for statics.
  • AnythingA class, a plain object, a service. Not a constructor.
  • OrderTwo addons patching the same method chain, in the order their bundles load.

The super in a patch is the code you replaced, not the parent class. Call it, unless you truly mean to drop it.

Topic 4 · State Management

State Management

Where a piece of state should live, who writes it, and how far it has to travel.

Shared state

Where should this state live?

Climb one rung at a time, and only when the one you are on hurts.

  • 1

    In the component

    A signal field. Most state stops here.

  • 2

    In a common ancestor

    Two components need it: lift it up, pass it down as a prop.

  • 3

    Plus a callback prop

    A child changes it by calling the owner, never by writing the prop.

  • 4

    In a plugin

    Too much plumbing: providePlugins above, usePlugin below.

  • 5

    In a global plugin

    It has to outlive the screen: services.add.

One owner per piece of state, and only the owner writes it.

Shared state

The same counter, three rungs up

  • The state is a signal at every rung. What changes is who holds it.

1 · the component owns it

class Counter extends Component {
    value = signal(0);
    increment() {
        this.value.set(this.value() + 1);
    }
}

2 and 3 · the parent owns it

class Parent extends Component {
    value = signal(0);
    increment = () => { /* ... */ };
}
<Child value="this.value"
       onIncrement.bind="this.increment"/>

4 and 5 · a plugin owns it

export class CounterPlugin extends Plugin {
    value = signal(0);
    double = computed(() => this.value() * 2);
    increment() {
        this.value.set(this.value() + 1);
    }
}

providePlugins([CounterPlugin]);  // 4 · one subtree
services.add(CounterPlugin);      // 5 · the whole tab

// anywhere below, no props
counter = usePlugin(CounterPlugin);

Rungs 4 and 5 are the same class. Only the line that installs it changes.

Shared state

What belongs in a plugin

The component renders. The plugin knows the rules. That split is the whole architecture.

A plugin holds

  • StateThe signals that actually change.
  • DerivationsA computed for everything that follows from them. Never store what you can derive.
  • IntentThe methods a component calls: buyBot(), not count.set(...) from three places.
  • Its own edgesThe server, the storage, the timers. Through another plugin when there is one.

And it buys you

  • One ownerEveryone reads the same signals. No copy to keep in sync.
  • No plumbingA component three levels down asks for the plugin. Nothing passes through the middle.
  • Fine grainA component re-renders only if it read the signal that changed.
  • TestableA plugin is a class with signals. Its rules can be tested without mounting anything.

Step 4 of the clicker game is this refactor: the game rules leave the components for good.

Reading old code

What became of env

  • In Owl 2, env was the shared object every component could reach, and useSubEnv the way to hand something down.
  • Owl 3 has neither. What you see in master comes from the compatibility layer.

What you will read

// still everywhere in addons/web
this.env.services.action
this.env.bus
this.env.debug
this.env.isSmall

// Owl 2, handing state down the tree
useSubEnv({ myCounter: this.counter });
this.counter = useState(this.env.myCounter);

Provided by @web/owl2/owl3_compatibility_layer.

What you write

// handing state down a subtree: useSubEnv's heir
providePlugins([ClickerPlugin]);

// reading it, anywhere below
clicker = usePlugin(ClickerPlugin);

// something the app was mounted with
const debug = useConfig("debug");
  • ProvideprovidePlugins is what useSubEnv became: it makes a plugin available to one subtree. services.add does the same for the whole tab.
  • ReadusePlugin is the other half — typed, asked for by class, and impossible to reach by accident. env was one bag for everything.

Recognize it, do not write it. env goes with the compatibility layer, and the code leaning on it goes too.
