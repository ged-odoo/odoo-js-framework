Topic 4 · Part 1

Views and Fields

What a view is made of whatever its type, the model behind the relational ones, and the components that plug into them.

ThenCustomizing views and fields

Views

What a view does

  • Loads data

    Through the ORM, from the model it is set on.

  • Structures it

    According to an arch: an xml document, stored in ir.ui.view.

  • Shows it

    Usually records and fields, though not always.

  • Edits

    Sometimes: a view can be read-only by design.

The debug tools (developer mode) are the fast way to read a view's actual arch.

Views

View architecture

The same shape whatever the type: a controller on top, a renderer and a model under it.

The renderer never calls the server, and the model never draws anything. They meet in the controller.

Views

The pieces of a view

  • ControllerThe main component: owns the model, holds the control panel and the renderer.
  • RendererBelow the control panel, the component that actually represents the data.
  • ModelLoads data from the database, and writes changes back to it.
  • ArchParserReads the arch and extracts the information the rest needs.
  • CompilerFor some views: turns the arch into an actual Owl template.

A view type registers all five together, under one name.

Views

Registering a view type

The same shape for every view: kanban, list, form...

export const kanbanView = {
    type: "kanban",
    ArchParser: KanbanArchParser,
    Controller: KanbanController,
    Model: RelationalModel,
    Renderer: KanbanRenderer,
    Compiler: KanbanCompiler,
    buttonTemplate: "web.KanbanView.Buttons",
    props: (genericProps, view) => {
        // whatever this returns is what the
        // controller is then created with
    },
};

registry.category("views").add("kanban", kanbanView);

The view's own props function is what feeds the controller the arch, the fields, the domain...

Views

Example: the form view

The same names, in the tree an actual form view mounts.

One component per <field> in the arch, and an x2many holds a renderer of its own: the same architecture, one level down.

Views

Standard flows

Editing a value

  • The user changes a value in a field's input.
  • That field instance calls update on props.record.
  • The relational model is notified of the change.
  • If there are onchanges, the server is called to get the new values.
  • The model updates, and every changed field rerenders.

Changing a domain in a list

  • The user changes the search filters.
  • WithSearch updates its domain.
  • The controller is updated with the new domain as a prop.
  • The relational model refetches the data.
  • The renderer updates, destroying its previous components.

Both flows go through the model - it is the one source of truth for a view's data.

Views

Odoo views

Three of them show records and their fields. The rest aggregate, schedule or plot the same data.

Relational views

  • form

    One record, and its fields.

  • list

    Many records, in rows.

  • kanban

    Many records, as cards.

The others

  • graph

    Totals, as a chart.

  • pivot

    Totals, in a table.

  • calendar

    Records on dates.

  • activity

    What is due, per record.

  • gantt

    Spans on a timeline.

  • map

    Records on a map.

Only the three on the left share the RelationalModel; the others bring their own. gantt and map are enterprise.

The model

The RelationalModel

One model behind form, list and kanban. What it manages is not a screen: it is collections of records, and the relations between them.

Records, groups of records and x2many lists are all DataPoints — one tree, loaded and saved in one call. many2many behaves like one2many here.

Fields

A field is a component

One <field> in the arch, one component on screen: a child of the renderer, bound to one value of one record.

the arch, in ir.ui.view

<form>
    <group>
        <field name="name"/>
        <field name="email"/>
        <field name="category_id"
               widget="many2many_tags"/>
    </group>
</form>

what the renderer mounts

<!-- FormRenderer, compiled from the arch -->
<Field name="'name'"
       record="this.props.record"/>
<Field name="'email'"
       record="this.props.record"/>
<Field name="'category_id'"
       record="this.props.record"/>

Simplified: the compiler also hands each one its id, the arch info that describes it, and the view's readonly state.

Same Field component every time. Which component it then renders is what the widget attribute, or the field's type, decides.

Fields and widgets

Two registries

Views are generic, but form, kanban and list allow two kinds of sub components: fields and widgets. Both can read and write the current record.

Fields

Registry: "fields"

<field name="module_stock_fleet"/>

The component is chosen from the field's type, or from the registry if widget= names one.

<field
    name="module_delivery_ups"
    widget="upgrade_boolean"/>

Widgets

Registry: "view_widgets"

<widget name="res_config_invite_users"/>

name is the key in the registry: a widget is not tied to a specific field.

Widgets

A view widget

Typically like a field, but reading whatever it needs off the record.

In the arch

<widget
    name="web_ribbon"
    title="Archived"
    bg_color="text-bg-danger"
    invisible="active"/>

ribbon_widget.js

class RibbonWidget extends Component {
    static template = "web.Ribbon";
    props = useProps({
        ...standardWidgetProps,
        text: t.string(),
        title: t.string().optional(),
        bgClass: t.string().optional(),
    });
    get classes() {
        return this.props.bgClass;
    }
}
const ribbonWidget = {
    component: RibbonWidget,
    extractProps: ({ attrs }) => ({
        text: attrs.title || attrs.text,
        title: attrs.tooltip,
        bgClass: attrs.bg_color,
    }),
};
registry.category("view_widgets").add("web_ribbon", ribbonWidget);

A widget receives the record, and everything extractProps pulls out of the arch, as props.

Fields

Every <field> tag spawns a field component.

Except basic fields in list and kanban views, kept as plain cells for performance.

Fields

Which component, for which field?

1. The widget attribute

<field name="category_ids" widget="many2many_tags"/>

If it is set, that name is looked up in the "fields" registry.

2. The field's type

<field name="contact_name"/>

Otherwise, the type (char, many2one...) picks a default component.

Fields

A field, from nothing

A component, a template, registered under a name.

hash_field.js

import { Component, useProps } from "@odoo/owl";
import { registry } from "@web/core/registry";

class HashField extends Component {
    static template = "web.HashField";
}

const hashField = {
    component: HashField,
};

registry.category("fields").add("hash", hashField);

hash_field.xml

<templates xml:space="preserve">
    <t t-name="web.HashField">
        Hello there
    </t>
</templates>

<field name="passkey" widget="hash"/> now renders "Hello there" wherever it is used.

Fields

Reading and writing the record

Fields get a default set of props: standardFieldProps.

hash_field.js

import { Component, useProps } from "@odoo/owl";
import { registry } from "@web/core/registry";
import { standardFieldProps } from "../standard_field_props";
import { createRandomString } from "./utils";

class HashField extends Component {
    static template = "web.HashField";

    props = useProps({ ...standardFieldProps });

    generate() {
        const randomHash = createRandomString(18);
        this.props.record.update({[this.props.name]: randomHash});
    }
}

const hashField = {
    component: HashField,
};

registry.category("fields").add("hash", hashField);

hash_field.xml

<t t-name="web.HashField">
    <div t-if="!this.props.record.data[this.props.name]">
        <button
            class="btn btn-secondary"
            t-on-click="this.generate">
            Generate
        </button>
    </div>
    <span t-out="this.props.record.data[this.props.name]"/>
</t>

record carries the data, update to write to it, plus fields, resId, resModel...

Fields

A field-specific prop, from the arch

For example, the hash's length.

  • ✗<field name="passkey" widget="hash" props="{ 'length': 12 }"/>
  • ✗<field name="passkey" widget="hash" length="12"/>
  • ✓<field name="passkey" widget="hash" options="{ 'hash_length': 12 }"/>

options is the arch's own way of passing arbitrary data to a field or a widget.

Fields

Extracting options from the arch, into props

const hashFieldProps = { ...standardFieldProps, length: t.number().optional() };

class HashField extends Component {
    static template = "web.HashField";

    props = useProps(hashFieldProps);

    generate() {
        const randomHash = createRandomString(this.props.length);
        this.props.record.update({[this.props.name]: randomHash});
    }
}

const hashField = {
    component: HashField,
    extractProps: ({ options }) => ({
        length: options.hash_length,
    }),
};

registry.category("fields").add("hash", hashField);

<field name="passkey" widget="hash" options="{ 'hash_length': 12 }"/>

Fields

extractProps

Turns arch data into component props. It takes two arguments.

fieldInfo

  • attrs, options
  • viewType
  • ...

What the arch said, and which view is asking.

dynamicInfo

  • readonly, required
  • context, domain()

What is true of this instance, right now.

priority_field.js — from addons/web

extractProps(fieldInfo, dynamicInfo) {
    return {
        withCommand: fieldInfo.viewType === "form",
        readonly: dynamicInfo.readonly,
    };
},
  • The componentTakes a withCommand prop. It never asks what view it is in.
  • extractPropsReads fieldInfo.viewType and decides. Defaulting or forcing a prop per view type is what it is for.

dynamicInfo is what lets several instances of the same field on a view behave differently.

Fields

Registering for one view type only

A field can be added under a view-specific name.

registry.category("fields").add("list.hash", listHashField);
registry.category("fields").add("kanban.hash", kanbanHashField);

// uncommon, but possible
registry.category("fields").add("form.hash", formHashField);

<field name="passkey" widget="hash"/> resolves to whichever entry matches the current view.
